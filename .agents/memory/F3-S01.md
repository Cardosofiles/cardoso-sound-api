## 1. O que foi entregue

A API Fastify v5 agora possui infraestrutura completa de autenticação e identidade integrada ao Better Auth v1.7.2 e PostgreSQL. A integração disponibiliza autenticação simultânea por Bearer token (via cabeçalho `Authorization: Bearer <token>` e emissão em `set-auth-token`, consumido pelo Flutter) e por cookies seguros HttpOnly (`better-auth.session_token`, consumido por browser e Swagger UI).

Foram entregues os endpoints nativos de cadastro, login, logout e sessão (`POST /api/auth/sign-up/email`, `POST /api/auth/sign-in/email`, `POST /api/auth/sign-out`, `GET /api/auth/get-session`), decorators universais `request.user` e `request.session` resolvidos passivamente em toda requisição via hook global `onRequest`, e o guard reutilizável `fastify.requireAuth` para proteção de rotas privadas (F3-S02, F4-S01 e F4-S02).

Além disso, foi disponibilizado o helper reutilizável `signUpAndGetToken(app, email?)` em `tests/e2e/helpers/auth.ts`, do qual quatro sprints subsequentes dependem diretamente.

## 4. Como funciona — o que o diff não conta

### A Ponte Fetch ↔ Fastify (`src/modules/auth/auth.plugin.ts`)

A integração entre o Better Auth e o Fastify converte `FastifyRequest` no objeto Fetch standard `Request` e devolve a resposta do `auth.handler(req)`:

```typescript
fastify.route({
  method: ['GET', 'POST', 'OPTIONS'],
  url: '/api/auth/*',
  schema: { hide: true }, // Desabilita serialização Zod — payload pertence ao Better Auth
  async handler(request, reply) {
    const url = new URL(request.url, env.BETTER_AUTH_URL);
    const headers = toFetchHeaders(request.headers);

    const hasBody =
      request.body !== undefined && request.method !== 'GET' && request.method !== 'HEAD';

    const req = new Request(url, {
      method: request.method,
      headers,
      body: hasBody ? JSON.stringify(request.body) : undefined,
    });

    const res = await auth.handler(req);

    reply.status(res.status);

    // Repasse atômico de múltiplos Set-Cookie via array (D-44)
    const setCookies = res.headers.getSetCookie();
    if (setCookies.length > 0) {
      void reply.header('set-cookie', setCookies);
    }

    // Repasse dos demais headers, excluindo set-cookie já repassado acima
    res.headers.forEach((value, key) => {
      if (key.toLowerCase() !== 'set-cookie') {
        void reply.header(key, value);
      }
    });

    const bodyText = await res.text();
    return reply.send(bodyText || null);
  },
});
```

### Repasse de Múltiplos Headers `Set-Cookie` (D-44 / Armadilha 1)

O Better Auth emite cookies HttpOnly para controle de sessão (`better-auth.session_token`). Ao utilizar `res.headers.forEach()`, muitos runtimes de HTTP concatenam cabeçalhos homônimos com vírgulas (`"cookie1=a, cookie2=b"`), tornando-os inválidos no navegador. Utilizar `res.headers.getSetCookie()` preserva o array nativo de strings, e o Fastify emite múltiplos cabeçalhos `Set-Cookie` separados no payload HTTP.

### Proxy Dinâmico de Banco de Dados (`dynamicDb`)

O Drizzle Adapter do Better Auth é instanciado em tempo de importação em `auth.config.ts`. Nos testes de integração com Testcontainers, o harness executa `setPool(testDb.pool)`, reatribuindo a variável singleton `db` de `src/db/client.ts`. Para evitar que o adapter fique preso à conexão inicial de desenvolvimento, configuramos um `Proxy` que resolve dinamicamente as chamadas de método (`select`, `insert`, `query`, etc.) para a instância ativa de `db`.

### Posição do Plugin em `src/app.ts`

```typescript
// 4. Rotas de monitoramento de saúde (liveness e readiness)
await app.register(healthPlugin);

// 5. Plugin de autenticação, decorators de sessão e guard global
await app.register(authPlugin);

// 6. Rotas de catálogo e domínio (/api/v1)
await app.register(artistsRoutes, { prefix: API_PREFIX });
await app.register(tracksRoutes, { prefix: API_PREFIX });
```

O `authPlugin` é obrigatoriamente registrado **antes** de qualquer rota de domínio para que os decorators `request.user` e `request.session` estejam instanciados e o hook global `onRequest` seja executado antes dos handlers de negócio.

### Assinatura de `signUpAndGetToken`

```typescript
export async function signUpAndGetToken(
  app: FastifyInstance,
  email?: string,
): Promise<{
  token: string;
  userId: string;
}>;
```

Cria um usuário aleatório via `POST /api/auth/sign-up/email`, extrai o Bearer token do header `set-auth-token` e o identificador único `user.id`.

## 6. Armadilhas encontradas

| Sintoma                                                              | Causa                                                                                         | Solução                                                                       |
| -------------------------------------------------------------------- | --------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------- |
| `The field "issuer" does not exist in the "account" schema`          | Better Auth v1.7.2 exige `issuer` na tabela `account` (gerado por `createLocalAccountIssuer`) | Adicionar `issuer` em `users.schema.ts` e gerar migração `0001_*.sql` (D-43). |
| Suíte falhava em T6 e T17 ao inspecionar container do Testcontainers | Drizzle adapter em `auth.config.ts` mantinha referência estática ao pool original             | Criar proxy dinâmico `dynamicDb` que delega para o `db` ativo do pool.        |
| Erro `boundaries/element-types` ao importar `auth.routes.ts`         | `plugin` não tem permissão de importar `routes` no ESLint                                     | Manter montagem da rota curinga em `auth.plugin.ts` e `export {}` em routes.  |
| Múltiplos cookies colapsavam se iterados com `forEach`               | `Headers.forEach` pode concatenar `Set-Cookie` com vírgula                                    | Usar `res.headers.getSetCookie()` repassando array para `reply.header()`.     |

## 1. Migração 0005 — Schema `rate_limit` (GAP-12)

### SQL Exato (`drizzle/0005_fearless_sinister_six.sql`)

```sql
CREATE TABLE "rate_limit" (
	"id" text PRIMARY KEY NOT NULL,
	"key" text NOT NULL,
	"count" integer NOT NULL,
	"last_request" bigint NOT NULL,
	CONSTRAINT "rate_limit_key_unique" UNIQUE("key")
);
```

### Justificativas e Conformidade

1. **4 Colunas Canônicas do Better Auth v1.7.2:**
   - `id`: Text PK gerada pelo Better Auth.
   - `key`: Chave canônica do bucket de rate limit (ex.: `127.0.0.1:/api/auth/sign-in/email`), protegida por constraint `UNIQUE` (`rate_limit_key_unique`).
   - `count`: Contador acumulado de requisições na janela temporal (`integer NOT NULL`).
   - `last_request`: Carimbo de data/hora em milissegundos da última requisição (`bigint NOT NULL` no PostgreSQL mapeado com `{ mode: 'number' }` no Drizzle).
2. **Conformidade de Schema:** Validada via `getAuthTables(auth.options)` em `tests/integration/schema-rate-limit.test.ts` (T24). Os campos `key` (único e obrigatório), `count` (obrigatório) e `lastRequest` (obrigatório) casam perfeitamente com a especificação gerada por `@better-auth/cli generate`.
3. **Persistência Relacional:** `src/modules/auth/auth.config.ts` recebeu `storage: 'database'` no bloco `rateLimit`, transferindo os buckets de rate limit do Better Auth de memória RAM efêmera para o PostgreSQL com reaproveitamento de conexão via `drizzleAdapter(db)`.

## 2. Gerador de Chave de Rate Limiting e Header de Sessão (GAP-11)

### Implementação em `src/plugins/rate-limit.plugin.ts`

1. **`extractSessionToken(headers)`:**
   - Extrai o token de sessão estritamente através dos headers HTTP da requisição, sem realizar queries ao banco de dados e sem depender de decorações do Fastify.
   - Suporta Bearer tokens (`authorization: Bearer <token>` case-insensitive).
   - Suporta cookies de sessão regulares (`better-auth.session_token=<token>`) e com prefixo de produção seguro (`__Secure-better-auth.session_token=<token>`).
   - Tolera cookies adicionais ou malformados com fallback silencioso para `null`.
2. **`rateLimitKeyGenerator(req)`:**
   - Para rotas `/api/auth/**`: Devolve **estritamente `req.ip`**, impedindo multiplicação artificial de cota em endpoints de autenticação onde credenciais inválidas poderiam ser usadas para burlar os limites.
   - Para rotas `/api/v1/**`: Se um token de sessão estiver presente, devolve `${req.ip}|${sha256(token).slice(0, 16)}`, atribuindo cotas individuais para diferentes sessões/usuários atrás de um mesmo NAT/Proxy. Se anônimo, devolve estritamente `req.ip`.
   - **Eliminação de Cast Inseguro:** O código anterior realizava `(req as unknown as { user?: { id: string } }).user`. O novo gerador não toca em `req.user`, mantendo tipagem estática pura e total independência da ordem de registro de plugins.

## 4. Endurecimento de Origens Confiáveis (GAP-18)

1. **Rejeição de Coringas em `CORS_ORIGIN`:**
   - Em produção (`NODE_ENV === 'production'`), cada origem listada em `CORS_ORIGIN` é validada contra a regex `^https?://[^*\s]+$`.
   - Origens com wildcard (`*`) provocam falha imediata na validação de `src/config/env.ts` com código de saída 1.
2. **Validação Estrita de `MOBILE_DEEP_LINK`:**
   - Declarado com regex estrita: `^[a-zA-Z][a-zA-Z0-9+.-]*://[a-zA-Z0-9._~:/?#\\[\\]@!$&'()*+,;=-]+$`.
   - Rejeita esquemas genéricos, coringas (`*`) e URLs malformadas em qualquer ambiente.
3. **Casos Cobertos em `tests/unit/config/env.test.ts` (T12–T20):**
   - Todos os cenários de validação positiva e negativa para `RATE_LIMIT_REDIS_URL`, `CORS_ORIGIN` e `MOBILE_DEEP_LINK` validados e 100% verdes.

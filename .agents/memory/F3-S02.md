## 1. O que foi entregue

Implementação e entrega completa do módulo de perfil do usuário autenticado (`/api/v1/me`), inaugurando as rotas protegidas por autenticação na API. O módulo permite a consulta segura do perfil (`GET /api/v1/me` — R13), a atualização cadastral parcial de nome e foto de perfil com proteção contra payload vazio (`PATCH /api/v1/me` — R14) e o encerramento definitivo da conta com exclusão em cascata coordenada de todas as sessões, credenciais e recursos associados no PostgreSQL (`DELETE /api/v1/me` — R15).

A implementação cumpre o padrão estrito de defesa em profundidade, garantindo que credenciais internas do Better Auth (como senhas com hash, tokens de sessão e status de verificação de e-mail) nunca sejam expostas.

## 4. Como funciona — o que o diff não conta

### Padrão de Rota Protegida com Clean Architecture

1. **Guard `onRequest` e Helper `getUserId` Seguro:**
   As rotas aplicam `{ onRequest: [fastify.requireAuth] }`. Para cumprir a proibição absoluta de asserções não-nulas (`@typescript-eslint/no-non-null-assertion`) sem utilizar `any`, a função utilitária `getUserId(request)` valida a presença de `request.user` em tempo de execução:

   ```typescript
   function getUserId(request: { user: { id: string } | null }): string {
     if (!request.user) {
       throw new UnauthorizedError('Authentication required');
     }
     return request.user.id;
   }
   ```

   Dessa forma, o handler extrai apenas o identificador atômico `string` e passa para o service. O service não recebe os objetos `request`/`reply` do Fastify.

2. **Defesa em Profundidade em Duas Camadas (Two-Tier Scrubbing):**
   - **Camada 1 (Banco):** O `UsersRepository.findById` e `.update` selecionam explicitamente `{ id, name, email, image, createdAt }`. A query `select *` é proibida para que colunas do Better Auth (`password`, `emailVerified`, `updatedAt`) nunca entrem na memória da aplicação.
   - **Camada 2 (Serialização):** O `meSchema` atua no `serializerCompiler` do Fastify, podando compulsoriamente qualquer campo excedente antes da resposta sair.

3. **Distinção Estrita de `image: null` vs `image: undefined`:**
   O `updateMeBodySchema` utiliza `image: z.url().nullable().optional()`. No repositório, `if (data.image !== undefined)` assegura que enviar `image: null` limpa o avatar no banco de dados para `NULL`, enquanto omitir `image` (`undefined`) preserva o valor atual da coluna.

4. **Corpo Vazio Rejeitado com 400 Bad Request:**
   O refinamento `.refine((data) => data.name !== undefined || data.image !== undefined)` garante que requisições `PATCH /me` com `{}` sejam interceptadas pelo compilador Zod e retornem HTTP 400 com envelope RFC 7807 (`{ statusCode: 400, error: 'Bad Request', ... }`).

5. **Exclusão Transacional e Cascade Delete no PostgreSQL:**
   `DELETE /me` invoca `UsersRepository.delete(userId)` encapsulado em `this.db.transaction()`. Como as tabelas `session`, `account`, `playlists` e `favorites` foram configuradas com `onDelete: 'cascade'` desde F2-S01, a deleção do registro pai na tabela `user` purga de forma atômica e irreversível todas as sessões e dados associados.

6. **Tipagem Exata de Respostas 204 no Fastify Zod Type Provider:**
   O schema OpenAPI de `DELETE /me` declara `response: { 204: z.void() }`. No Fastify v5, o tipo `SendArgs<ReplyType>` exige parâmetros caso `ReplyType` seja `null`, mas torna o argumento opcional quando `ReplyType` é `void`. O uso de `z.void()` permite que `reply.status(204).send()` compile sem parâmetros e emita uma resposta HTTP sem corpo, prevenindo advertências de runtime.

## 6. Armadilhas encontradas

| Sintoma                                                                   | Causa                                                                                                                         | Solução                                                                                                                                                |
| ------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `Argument of type '204' is not assignable to parameter of type '401'`     | Omitir 204 do schema de resposta faz o Fastify restringir os status válidos em `reply.status()` exclusivamente aos declarados | Declarar explicitamente a resposta 204 no schema Fastify Zod.                                                                                          |
| `Expected 1 arguments, but got 0` ao chamar `reply.status(204).send()`    | `response: { 204: z.null() }` força o tipo de `SendArgs<null>` a esperar obrigatoriamente `[payload: null]`                   | Utilizar `204: z.void()`. O Fastify Type Provider infere `void`, tornando o payload opcional em `SendArgs<void>` e permitindo `send()` sem argumentos. |
| `error: Forbidden non-null assertion` no ESLint                           | `@typescript-eslint/no-non-null-assertion` proíbe o operador `!` em `request.user!.id`                                        | Criar o type guard `getUserId(request)` que valida o usuário e lança `UnauthorizedError` caso nulo.                                                    |
| `error: Placing a void expression inside another expression is forbidden` | Teste T8 chamava `expect(service.deleteMe()).toBeUndefined()`, capturando retorno de função `void`                            | Executar `await service.deleteMe()` como declaração isolada e asserir a chamada no repositório mockado.                                                |

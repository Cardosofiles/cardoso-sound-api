## 4. Como funciona — o que o diff não conta

1. **Ordem dos steps no GitHub Actions:** `pnpm/action-setup@v4` é invocado antes de `actions/setup-node@v4` para permitir que o setup do Node configure o cache nativo do pnpm (`cache: pnpm`). A versão do pnpm é omitida do step de setup para ser inferida automaticamente do campo `packageManager` em `package.json`, evitando conflitos de versão duplicada.
2. **Ambiente para testes unitários no CI:** Em virtude da validação estrita introduzida em F1-S03 (`src/config/env.ts`), que chama `process.exit(1)` caso `DATABASE_URL` e `BETTER_AUTH_SECRET` não estejam presentes, o job `ci` injeta variáveis dummy seguras (`NODE_ENV: test`, `DATABASE_URL: postgresql://cardoso:cardoso_dev@localhost:5432/cardoso_sound`, `BETTER_AUTH_SECRET: troque-por-um-segredo-de-no-minimo-32-caracteres`) no nível do job, garantindo que o runtime de testes e a importação de módulos de configuração ocorram sem dependência de arquivo `.env` físico no runner.
3. **Bloqueio de push direto pelo Ruleset:** O ruleset `protection-develop` e `protection-main` foram configurados com a regra `required_status_checks` (`context: "ci"` e `strict_required_status_checks_policy: true`).

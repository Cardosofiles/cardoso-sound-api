## 1. O que foi entregue

Implementação dos fluxos finais de autenticação e identidade da API:

1. **Autenticação Social OAuth (R26, R27):** Suporte nativo aos provedores Google, GitHub e Facebook. Registro condicional via `SOCIAL_PROVIDERS`, escopos mínimos autorizados (`openid email profile`, `user:email`, `email public_profile`) e vinculação automática segura de contas (`accountLinking: true` com `trustedProviders: ['google', 'github']`).
2. **Módulo de E-mail Transacional Desacoplado:** Arquitetura com interface canônica `Mailer`, templates HTML puros e dois transportes integrados: `memoryMailer` (com `outbox` reativo e inspecionável para testes e desenvolvimento) e `resendMailer` (baseado no SDK oficial `resend` com sanitização estrita de URLs e tokens nos logs).
3. **Verificação de E-mail (R28, R29):** Envio automático de link de confirmação no cadastro e reenvio sob demanda (`POST /api/auth/send-verification-email`), com confirmação transacional de titularidade via token único (`GET /api/auth/verify-email`).
4. **Recuperação e Redefinição de Senha (R30, R31):** Endpoint seguro de solicitação de redefinição (`POST /api/auth/forget-password`), sem enumeração de usuários, e atualização atômica de credenciais (`POST /api/auth/reset-password`) com tokens descartáveis expirando em 1 hora.
5. **Defesa e Proteção de Borda:** Rate limits granulares específicos por rota (`customRules`), validação de `trustedOrigins` incluindo deep links mobile contra open redirect e desativação de bypass de origem em testes (`disableOriginCheck: false`).

## 4. Como funciona — o que o diff não conta

### 4.1 Injeção Dinâmica e Testabilidade Sem Quebrar o Single Fork

O Better Auth compila seu roteador e provedores no momento em que `betterAuth({...})` é executado. Para permitir que a suíte de testes de integração configure provedores sociais pontualmente (como o Google em T21) sem sujar variáveis globais de ambiente nem reiniciar o processo do Vitest (`singleFork: true`), a configuração foi estruturada com uma fábrica pura e um proxy transparente:

```typescript
export function createAuth(options?: CreateAuthOptions) {
  return betterAuth({ ... });
}

const defaultAuth = createAuth();
let currentAuth = defaultAuth;

export const auth = new Proxy(defaultAuth, {
  get<K extends keyof typeof defaultAuth>(_target: typeof defaultAuth, prop: K) {
    const targetAuth = currentAuth;
    const value = targetAuth[prop];
    if (typeof value === 'function') {
      return (value as (...args: unknown[]) => unknown).bind(targetAuth);
    }
    return value;
  },
});
```

A função `setAuthInstanceForTest` permite que testes de integração injetem instâncias especializadas mantendo total conformidade de tipos com `typeof auth.$Infer`.

### 4.2 Por que `requireEmailVerification: false` (Decisão D-46)

O Better Auth possui a diretiva `requireEmailVerification: true`, que rejeita com HTTP 403 qualquer tentativa de sign-in de usuário que ainda não clicou no link de confirmação.
No entanto, no Cardoso Sound, o helper E2E `signUpAndGetToken` (utilizado intensivamente nas suítes das Fases 3, 4 e 5) depende da emissão imediata de tokens no cadastro. Bloquear sign-in preventivamente quebraria todos os fluxos automatizados.
Portanto, a verificação de e-mail é disparada e registrada na coluna `email_verified`, mas a restrição de acesso por e-mail verificado é desacoplada e será ativada apenas se uma regra de negócio futura explicitamente o exigir.

### 4.3 Isolamento de Tokens e Proteção de Logs no ResendMailer

Tokens de reset de senha e verificação de e-mail trafegam nas URLs. Nos templates (`templates.ts`), os tokens aparecem exclusivamente no atributo `href="..."` da tag `<a>`, jamais no corpo legível do e-mail.
No logger, o transporte `memoryMailer` emite a URL em nível `info` para agilizar o desenvolvimento local, enquanto o transporte `resendMailer` **nunca loga a URL**, emitindo apenas `{ to, subject }` para evitar que tokens vazem para coletores de logs em produção. Além disso, se o serviço do Resend falhar ou estiver fora do ar, o método `send` captura o erro, emite um `warn` defensivo e resolve sem lançar exceção, impedindo a interrupção do fluxo de sign-up do usuário (Armadilha 1).

### 4.4 Inspecionando o `outbox` em Testes e Desenvolvimento

Em ambientes onde `RESEND_API_KEY` não está presente (desenvolvimento local e testes), o `memoryMailer` é acionado automaticamente. Os e-mails despachados são acumulados na lista em memória `outbox`:

```typescript
import { clearOutbox, outbox } from '@/shared/email/mailer';

// Inspeciona mensagens enviadas
expect(outbox).toHaveLength(1);
expect(outbox[0].to).toBe('usuario@exemplo.com');

// Limpa buffer antes de cada teste
clearOutbox();
```

## 5. Integração Mobile (Flutter) — Guias de Implementação

O aplicativo mobile Flutter dispõe de duas abordagens para concluir a autenticação social com o backend:

### Opção A: Fluxo com `idToken` Nativo (Recomendado)

O aplicativo utiliza os plugins nativos do Google (`google_sign_in`) ou Facebook para realizar o fluxo de login diretamente no sistema operacional (Google Play Services / iOS Authentication Services). O token de identidade obtido é despachado diretamente para a API:

```http
POST /api/auth/sign-in/social
Content-Type: application/json

{
  "provider": "google",
  "idToken": "<GOOGLE_ID_TOKEN_EMITIDO_PELO_SDK_NATIVO>"
}
```

**Vantagens:**

- Experiência fluida (One-Tap Sign-In no Android, FaceID/Apple Keychain no iOS).
- Não há abertura de navegador externo.
- Não depende de captura de deep links ou callbacks de URL.

### Opção B: Fluxo com Navegador Externo + Deep Link

O aplicativo solicita o início do fluxo enviando seu esquema de deep link pré-autorizado em `callbackURL`:

```http
POST /api/auth/sign-in/social
Content-Type: application/json

{
  "provider": "google",
  "callbackURL": "cardososound://auth"
}
```

**Resposta do backend:**

```json
{
  "url": "https://accounts.google.com/o/oauth2/v2/auth?response_type=code&client_id=...&redirect_uri=http%3A%2F%2Flocalhost%3A3333%2Fapi%2Fauth%2Fcallback%2Fgoogle&...",
  "redirect": true
}
```

O Flutter abre a URL no navegador do sistema (`url_launcher` ou Custom Tabs / ASWebAuthenticationSession). Após consentimento do usuário, o backend processa o callback e redireciona o cliente para o `callbackURL`:

```
cardososound://auth?token=<SESSION_TOKEN>
```

O aplicativo intercepta o deep link via pacote `app_links`, extrai o Bearer token e inicializa a sessão local.

## 6. Cobertura de Testes (T1 a T26)

Todos os 26 casos previstos foram implementados e validados:

- **T1 a T3b (Unitários — Mailer):** Acúmulo no outbox sem chave, chamada do cliente Resend com parâmetros corretos, resiliência defensiva a exceções e log warn.
- **T4 a T6 (Unitários — Templates):** Renderização de URLs exatas em `href`, assunto não-vazio e garantia de que nenhum token é renderizado fora do atributo `href`.
- **T7 a T13 (Integração — Verificação de E-mail):** Envio automático no sign-up, sign-in funcional sem verificação prévia, marcação de `email_verified: true` no banco, uso único do token, rejeição de tokens adulterados, reenvio idempotente e proteção contra enumeração de e-mails existentes.
- **T14 a T20 (Integração — Recuperação de Senha):** Envio de link de reset sem vazamento de enumeração, redefinição com senha nova, rejeição da senha antiga (401), uso único de token de reset, rejeição de senhas menores que 8 caracteres e inspeção do comportamento de persistência de sessões prévias (D-46).
- **T21 a T26 (Integração — Social e Segurança):** Início de fluxo social Google gerando redirect para `accounts.google.com`, retorno 4xx para provedor inexistente (não 500), retorno 4xx para provedor sem credenciais no env (prova de registro condicional), rejeição de callbacks com `state` adulterado sem inserção na base, bloqueio de `callbackURL` externa não-autorizada (`trustedOrigins`) e verificação de que rate limits permanecem inativos em ambiente de teste (D-19).

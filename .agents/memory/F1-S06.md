## 1. O que foi entregue

A API Fastify v5 agora inicializa com a pilha completa de segurança e resiliência de borda:
cabeçalhos defensivos (`@fastify/helmet`), CORS permissivo em dev e restrito em produção expondo `set-auth-token` (`@fastify/cors`), rate limit global protegido por allowlist (`@fastify/rate-limit`), monitoramento de pressão de memória e event loop com degradação graciosa (`@fastify/under-pressure`), e documentação OpenAPI 3.0.3 interativa servida via Swagger UI (`/docs`).

Além disso, foram entregues os endpoints de observabilidade `GET /health` (liveness, 200 fixo) e `GET /health/ready` (readiness, 200 se `SELECT 1` responder ou 503 se o Postgres falhar), integrados a uma instância centralizada de `pg.Pool` e Drizzle ORM em `src/db/client.ts`. A fase F1 é concluída com 39 testes automatizados passando e preparação da tag `v0.1.0`.

## 4. Como funciona — o que o diff não conta

### Ordem de Registro de Plugins em `src/app.ts`

A ordem estrita de registro foi consolidada como:

```
1. Type Provider Zod (setValidatorCompiler, setSerializerCompiler)
2. errorHandlerPlugin (primeiro, para capturar falhas em hooks de todos os demais)
3. helmetPlugin (antes de CORS para que headers defensivos não sobrescrevam CORS)
4. corsPlugin
5. rateLimitPlugin
6. underPressurePlugin
7. swaggerPlugin (OpenAPI + Swagger UI)
8. healthPlugin (/health e /health/ready)
```

> **Atenção para F3-S01 (Better Auth):** O `auth.plugin.ts` deverá ser registrado **imediatamente após** o `swaggerPlugin` e **antes** de qualquer rota de domínio `/api/v1/*`, decorando `request.user` e `request.session`.

### Bypass de Pressão em Sondas de Health

O `@fastify/under-pressure` derruba a API inteira devolvendo HTTP 503 se `checkDatabase()` retornar `false`. Se as rotas `/health*` sofressem essa interrupção, o orquestrador (Railway) assumiria que o processo Node morreu e o reiniciaria em loop (crash loop).
Para prevenir isso, `/health` e `/health/ready` utilizam `config: { pressureHandler: () => {} }`, permitindo que `/health` sempre responda 200 (liveness) e `/health/ready` responda 503 com payload próprio `{ status: 'unavailable', database: 'down' }` (readiness).

### Proteção de Idle Clients no `pg.Pool`

Quando um container Postgres é desligado via `docker stop`, o PostgreSQL envia um pacote `57P01` ("terminating connection due to administrator command") para conexões ativas. Em Node.js, `pg.Pool` emite um evento de erro em clientes ociosos; sem um listener registrado (`pool.on('error', ...)`), o EventEmitter dispara um `uncaughtException`. Registramos o listener defensivo em `src/db/client.ts` e na suíte de testes.

## 6. Armadilhas encontradas

| Sintoma                                                             | Causa                                                                         | Solução                                                                     |
| ------------------------------------------------------------------- | ----------------------------------------------------------------------------- | --------------------------------------------------------------------------- |
| Swagger UI falhava com `Refused to execute inline script`           | CSP do Helmet bloqueava os assets do Swagger UI fora de produção              | `contentSecurityPolicy: env.NODE_ENV === 'production' ? undefined : false`  |
| `uncaughtException` (código `57P01`) ao parar container de Postgres | `pg.Pool` emite erro em idle clients ao desconectar abruptamente              | Registrar `pool.on('error', () => {})` no pool singleton e no pool de teste |
| Erro `boundaries/element-types` no `client.ts`                      | Regra de arquitetura não previa imports intra-elemento no diretório `src/db/` | Adicionar `'db'` nas permissões `from: 'db'` em `eslint.config.mjs`         |

## 1. Migração 0004 — Schema Passkey (GAP-03 e GAP-09)

### SQL Exato (`drizzle/0004_eager_argent.sql`)

```sql
CREATE TABLE "passkey" (
	"id" text PRIMARY KEY NOT NULL,
	"name" text,
	"public_key" text NOT NULL,
	"user_id" text NOT NULL,
	"credential_id" text NOT NULL,
	"counter" integer NOT NULL,
	"device_type" text NOT NULL,
	"backed_up" boolean NOT NULL,
	"transports" text,
	"created_at" timestamp DEFAULT now() NOT NULL,
	"aaguid" text,
	CONSTRAINT "passkey_credential_id_unique" UNIQUE("credential_id")
);
--> statement-breakpoint
ALTER TABLE "passkey" ADD CONSTRAINT "passkey_user_id_user_id_fk" FOREIGN KEY ("user_id") REFERENCES "public"."user"("id") ON DELETE cascade ON UPDATE no action;--> statement-breakpoint
CREATE INDEX "passkey_user_id_idx" ON "passkey" USING btree ("user_id");
```

### Justificativas Arquiteturais

1. **11 Colunas Canônicas (Spec 08 §6.3):**
   - `id`: Text PK gerada pelo Better Auth.
   - `name`: Apelido opcional da chave escolhido pelo usuário (ex.: "MacBook Touch ID", "YubiKey 5C").
   - `public_key`: Chave pública FIDO2 codificada utilizada para verificar a assinatura da asserção criptográfica.
   - `user_id`: FK para `user(id)` com constraint estrita `ON DELETE CASCADE` (GAP-09). Ao excluir o usuário via `DELETE /api/v1/me` (R15), todas as passkeys vinculadas são expurgadas na mesma transação.
   - `credential_id`: Identificador único da credencial FIDO2 emitido pelo autenticador, protegido por constraint `UNIQUE` em nível de banco de dados (`passkey_credential_id_unique`) para prevenir colisões ou reuso fraudulento.
   - `counter`: Contador de assinaturas monotônico gerenciado pelo autenticador para detecção de clones.
   - `device_type`: Tipo do autenticador (`singleDevice` ou `multiDevice`).
   - `backedUp`: Flag booleana indicando sincronização em nuvem (ex.: iCloud Keychain, Google Password Manager).
   - `transports`: Transportes suportados pela credencial (ex.: `internal`, `usb`, `nfc`, `ble`).
   - `created_at`: Carimbo de data/hora de vinculação da credencial.
   - `aaguid`: Identificador do modelo de autenticador FIDO2 (AAGUID).
2. **Índice B-Tree `passkey_user_id_idx`:** Otimiza consultas frequentes por `user_id` em `list-user-passkeys` e operações em cascata de exclusão.
3. **Migração Versionada:** Gerada via `pnpm db:generate` e aplicada no PostgreSQL local via `pnpm db:migrate`. O comando destrutivo `pnpm db:push` **nunca** foi utilizado.

## 2. Configuração do Better Auth (`auth.config.ts`)

### Pacote e Derivação de Origem (D-32 e D-54)

- **Instalação:** `@better-auth/passkey@1.7.2` adicionado com versão idêntica (`^1.7.2` correspondente a `better-auth@1.7.2`), sem alterar `pnpm.onlyBuiltDependencies` pois o pacote não possui scripts de compilação C/C++.
- **Derivação de `rpID` e `origin` (D-54):**
  ```ts
  passkey({
    rpID: new URL(env.BETTER_AUTH_URL).hostname,
    rpName: 'Cardoso Sound',
    origin: env.BETTER_AUTH_URL,
  }),
  ```
  - Em desenvolvimento (`BETTER_AUTH_URL="http://localhost:3333"`), `rpID` resolve estritamente para `'localhost'`, sem porta nem esquema.
  - Em produção (`BETTER_AUTH_URL="https://api.cardososound.com"`), `rpID` resolve para `'api.cardososound.com'`.
  - `origin` recebe `env.BETTER_AUTH_URL` sem barra final, evitando rejeições em checagens de WebAuthn clientData.
  - `requireSession` mantém o valor padrão `true` (D-54): o registro de passkey exige autenticação prévia de um usuário ativo (via sessão cookie ou bearer token).
- **Ordem de Registro:** `passkey` é posicionado após `twoFactor` e antes de `bearer`, garantindo que os hooks de sessão e rate limiting operem de forma consistente.

### Rate Limiting de Autenticação (`AUTH_RATE_LIMIT_RULES`)

O dicionário `AUTH_RATE_LIMIT_RULES` foi expandido de 12 para 13 regras, integrando a regra canônica mandatória da Spec 08 §3.3:

- `'/sign-in/passkey'`: `{ window: 60, max: 10 }` (10 tentativas de autenticação por passkey por minuto por IP).

Com isso, todos os 13 endpoints críticos de autenticação estão blindados por rate limiting customizado.

## 3. Particularidades Técnicas e Descobertas (`better-auth@1.7.2`)

1. **Proteção Anti-Enumeração e Isolamento Multi-inquilino (D-31):**
   - No gerenciamento de passkeys (`POST /api/auth/passkey/delete-passkey` e `POST /api/auth/passkey/update-passkey`), quando um usuário autenticado tenta excluir ou renomear uma credencial pertencente a outro usuário, o Better Auth aplica seu middleware interno de posse (`requireResourceOwnership`) e rejeita a operação com **HTTP 404 (Not Found)** ou 401.
   - Ele **nunca** retorna 403 (Forbidden), respeitando rigorosamente a diretriz D-31 e a Spec 03 §7: recurso alheio e recurso inexistente são estritamente indistinguíveis para evitar enumeração de IDs.
2. **Endpoints de Desafio:**
   - `/api/auth/passkey/generate-register-options`: Rota `GET` protegida que gera o challenge FIDO2 para criação de credencial (`navigator.credentials.create`). Rejeita requisições sem sessão com 401.
   - `/api/auth/passkey/generate-authenticate-options`: Rota `GET` pública que emite o challenge de autenticação (`navigator.credentials.get`) contendo `rpId: 'localhost'`.
3. **Listagem Privada e Higienização de Dados:**
   - `GET /api/auth/passkey/list-user-passkeys`: Rota `GET` protegida que lista apenas as credenciais do usuário autenticado. Garante isolamento estrito: o Usuário B não vê as chaves cadastradas pelo Usuário A.
4. **Coexistência com Autenticação Tradicional:**
   - A adição de passkeys é 100% retrocompatível: usuários sem passkey continuam se autenticando normalmente por e-mail e senha (`POST /api/auth/sign-in/email`).

## 4. Runbook de Verificação no Navegador (WebAuthn / FIDO2)

Para testar e validar o fluxo de ponta a ponta com um navegador real:

1. **Iniciar a API em modo de desenvolvimento:**
   ```bash
   pnpm dev
   ```
2. **Abrir o Chrome DevTools e Ativar o Autenticador Virtual:**
   - Abra o Google Chrome em `http://localhost:3333/docs`.
   - Abra o menu DevTools (`F12`), vá em **More tools** -> **WebAuthn**.
   - Marque a opção **Enable virtual authenticator environment**.
   - Crie um autenticador virtual com as opções:
     - **Protocol:** `ctap2`
     - **Transport:** `internal`
     - **Supports resident keys:** Marcado
     - **Supports user verification:** Marcado
3. **Fluxo de Registro de Passkey:**
   - Autentique-se com um usuário via `POST /api/auth/sign-in/email` para obter cookie/bearer token.
   - Chame `GET /api/auth/passkey/generate-register-options` passando o cabeçalho de autenticação.
   - Repasse as opções geradas para a API WebAuthn do navegador (`navigator.credentials.create({ publicKey: options })`).
   - Envie o resultado para `POST /api/auth/passkey/verify-registration` com `{ name: "Meu Navegador", response: credential }`.
   - A credencial é persistida na tabela `passkey` do PostgreSQL.
4. **Fluxo de Autenticação sem Senha:**
   - Chame `GET /api/auth/passkey/generate-authenticate-options` para obter o challenge.
   - Execute `navigator.credentials.get({ publicKey: options })`.
   - Envie a resposta para `POST /api/auth/sign-in/passkey` com `{ response: assertion }`.
   - O Better Auth valida a assinatura criptográfica e retorna a sessão autenticada (`set-auth-token` / cookie).

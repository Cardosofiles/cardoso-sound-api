## 1. O que foi entregue

Entrega do módulo central do catálogo da API, permitindo que o app Flutter liste, busque, filtre e reproduza músicas diretamente sem necessidade de autenticação:

- `GET /api/v1/tracks` (R06): listagem paginada (`page`, `limit`), busca textual case-insensitive (`ILIKE`) em `tracks.title`, `tracks.album` e `artists.name`, filtro categórico por `genre` (enum 6 valores), filtro relacional por `artistId` (UUID) e ordenação dinâmica (`sort`: `recent`, `title`, `duration` com desempate por `id ASC`).
- `GET /api/v1/tracks/:id` (R07): consulta detalhada de faixa por UUID v4, com objeto `artist: ArtistSummary` embutido (`id`, `name`, `avatarUrl`) e sem chaves brutas de banco (`artist_id` ou `artistId`), emitindo 404 para identificador inexistente e 400 para ID não-UUID.
- `GET /api/v1/genres` (R08): lista fechada de 6 gêneros ordenados alfabeticamente (`genre ASC`) com a contagem total de faixas (`trackCount`) estritamente numérica, sem paginação e sem meta.

## 4. Como funciona — o que o diff não conta

1. **Projeção Estruturada Nativa via Drizzle ORM (Decisão D-41):**
   - O repositório realiza `db.select({ ...campos, artist: { id: artists.id, name: artists.name, avatarUrl: artists.avatarUrl } }).from(tracks).innerJoin(artists, eq(tracks.artistId, artists.id))`.
   - O Drizzle ORM nativamente preserva a estrutura declarada no select, emitindo o nó `artist` aninhado diretamente, dispensando pós-processamento e prevenindo o vazamento de colunas cruas (`artistId` ou `artist_id`).

2. **Simetria Rigorosa entre Query de Dados e Query de `count()`:**
   - A mesma instância de `whereClause` e o mesmo `innerJoin(artists)` são aplicados à query de paginação e à query `COUNT(*)`. O join com `artists` é indispensável no count porque o termo de busca textual (`search`) avalia `artists.name`. Sem o join, o PostgreSQL emitiria `missing FROM-clause entry for table "artists"`.

3. **Ordenação Determinística com Desempate Estável:**
   - Todo `orderBy` inclui `asc(tracks.id)` como critério secundário. Isso impede repetição ou omissão de linhas entre as páginas durante a navegação.

4. **Cast Explícito de BigInt em `listGenres`:**
   - O driver `node-postgres` retorna contagens `COUNT(*)` como string (`bigint`). O repositório aplica `sql<number>\`count(*)::int\`.mapWith(Number)`, assegurando que o serializador Zod receba `number` estrito e não falhe com HTTP 500.

5. **Sanitização de Caracteres Curinga:**
   - O parâmetro `search` escapa caracteres `%`, `_` e `\` com `replace(/[%_\\]/g, '\\$&')`, evitando casamento indevido do catálogo inteiro.

6. **Validação do Índice GIN e `EXPLAIN ANALYZE`:**
   - Consulta executada no banco com os 40 registros do seed:
     ```
     EXPLAIN ANALYZE SELECT * FROM tracks WHERE title ILIKE '%love%';
     Seq Scan on tracks (cost=0.00..10.38 rows=1 width=2206) (actual time=0.055..0.056 rows=0 loops=1)
       Filter: ((title)::text ~~* '%love%'::text)
     ```
   - O planejador escolhe `Seq Scan` porque com 40 linhas uma varredura sequencial em 1 bloco é ordens de grandeza mais rápida do que abrir o índice GIN.
   - Forçando `SET enable_seqscan = OFF;`, o índice é acionado imediatamente:
     ```
     Bitmap Heap Scan on tracks (cost=21.48..25.49 rows=1 width=2206) (actual time=0.156..0.156 rows=0 loops=1)
       Recheck Cond: ((title)::text ~~* '%love%'::text)
       ->  Bitmap Index Scan on tracks_title_trgm_idx (cost=0.00..21.48 rows=1 width=0)
     ```
   - Isso comprova que `tracks_title_trgm_idx`, `tracks_album_trgm_idx` e `artists_name_trgm_idx` estão 100% corretos e operantes para quando o catálogo escalar.

## 4. Como funciona — o que o diff não conta

1. O Husky 9 dispensa shebang e imports de inicializadores antigos (`husky.sh`), executando diretamente os scripts via runner do pnpm.
2. O commit inicial foi realizado diretamente na branch `main` apenas para viabilizar a criação do repositório público via `gh repo create --source=. --push`. Imediatamente em seguida, a branch `develop` foi enviada ao remoto e definida como branch padrão.
3. Os rulesets no GitHub foram configurados via `gh api` com bloqueio de push direto, deleção e force-push, além de exigir linear history e Pull Request. O status check `ci` não foi adicionado neste momento porque a suíte de CI só será criada em F1-S04; isso ficou anotado como pendência.
4. As reconciliações documentais mantiveram todos os placeholders de tokens seguros em `.agents/mcp_config.json` e removeram completamente menções a pacotes/ferramentas revogados (Playwright, Neon, RBAC, endpoints de streaming).

## 6. Armadilhas encontradas

| Sintoma                                           | Causa                                                                     | Solução                                                                        |
| ------------------------------------------------- | ------------------------------------------------------------------------- | ------------------------------------------------------------------------------ |
| `gh ruleset create` via comando direto não existe | A versão instalada do `gh` (2.46) suporta ruleset em modo somente leitura | Utilizada a REST API via `gh api --method POST /repos/{owner}/{repo}/rulesets` |
| Husky falha no `pnpm prepare` antes do `git init` | Sem repositório `.git`, o comando `husky` aborta                          | Executar `git init -b main` antes de `pnpm prepare`                            |

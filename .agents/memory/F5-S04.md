## 1. Migração 0002 — Índices do Schema Better Auth (GAP-16 e GAP-19)

### SQL Exato (`drizzle/0002_oval_talisman.sql`)

```sql
CREATE INDEX "account_user_id_idx" ON "account" USING btree ("user_id");--> statement-breakpoint
CREATE UNIQUE INDEX "account_provider_account_unique" ON "account" USING btree ("provider_id","account_id");--> statement-breakpoint
CREATE INDEX "session_user_id_idx" ON "session" USING btree ("user_id");--> statement-breakpoint
CREATE INDEX "verification_identifier_idx" ON "verification" USING btree ("identifier");
```

### Por que são exatamente quatro comandos?

1. **`session_user_id_idx`:** A tabela `session` possuía índice primário em `id` e índice único em `token`, mas não em `user_id`. O expurgo de sessões no encerramento de conta (`DELETE /api/v1/me` / R15) e na revogação em cascata no reset de senha (D-52) realizava varredura sequencial (`Seq Scan`) na tabela `session`.
2. **`account_user_id_idx`:** Pelo mesmo motivo, consultas relacionais e expurgo de contas vinculadas ao usuário realizavam varredura sequencial em `account`.
3. **`verification_identifier_idx`:** A tabela `verification` armazena tokens de confirmação de e-mail e recuperação de senha. A busca por e-mail (`identifier`) ocorria sem índice.
4. **`account_provider_account_unique`:** Restrição de unicidade composta fundamental (`provider_id`, `account_id`) para prevenir a corrida de colisão de contas OAuth (GAP-16). Prepara o terreno para o sprint F5-S10 (vínculo de múltiplas contas sociais).

A migração foi gerada via `pnpm db:generate`, auditada e aplicada via `pnpm db:migrate`. O comando proibido `pnpm db:push` **nunca** foi executado.

## 2. Transformação de Envelope de Erro RFC 7807 (`toRfc7807`) (GAP-26)

### Regras de Transformação

O envelope é **estritamente aditivo** (spec `08` §8.4):

- Preserva integralmente `code` e `message` no topo do JSON retornado pelo Better Auth (vital para o SDK oficial e o cliente Flutter).
- Adiciona os campos canônicos da API: `statusCode`, `error` (descrição HTTP canônica) e `details: null`.
- Só atua em respostas HTTP com `status >= 400`.
- Se o corpo não for um JSON parseável (ex: texto simples ou HTML de proxy), repassa-o intacto.
- Se o payload JSON contiver `error` em formato de objeto (ex: `{ error: { code, message } }`), unifica `code` e `message` na raiz e mapeia o status textual em `error`.

### Exemplos de Cargas (Antes e Depois) — Referência para o App Flutter

#### Caso 1: Credenciais Inválidas (`POST /api/auth/sign-in/email`)

**Antes (Better Auth puro):**

```json
{
  "code": "INVALID_EMAIL_OR_PASSWORD",
  "message": "Invalid email or password"
}
```

**Depois (com envelope RFC 7807 aditivo da API):**

```json
{
  "code": "INVALID_EMAIL_OR_PASSWORD",
  "message": "Invalid email or password",
  "statusCode": 401,
  "error": "Unauthorized",
  "details": null
}
```

#### Caso 2: Tentativa de Acesso a E-mail Não Verificado (`POST /api/auth/sign-in/email`)

**Antes:**

```json
{
  "code": "EMAIL_NOT_VERIFIED",
  "message": "Email not verified"
}
```

**Depois:**

```json
{
  "code": "EMAIL_NOT_VERIFIED",
  "message": "Email not verified",
  "statusCode": 403,
  "error": "Forbidden",
  "details": null
}
```

#### Caso 3: Validação de Payload com Erro Estruturado

**Antes:**

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Invalid email"
  }
}
```

**Depois:**

```json
{
  "code": "VALIDATION_ERROR",
  "message": "Invalid email",
  "statusCode": 400,
  "error": "Bad Request",
  "details": null
}
```

## 3. Gestão do Header `content-length` na Ponte Fastify (Armadilha 1)

O recálculo de headers ao interceptar a resposta do Better Auth revelou que o header `content-length` retornado pelo Better Fetch refletia o tamanho do JSON pré-transformação. Se fosse repassado ao cliente HTTP real, o corpo truncaria (ou o cliente aguardaria timeout de conexão).

**Ação executada em `src/modules/auth/auth.plugin.ts`:**
O header `content-length` foi explicitamente excluído do repasse na ponte Fastify, junto com `set-cookie`:

```ts
for (const [key, value] of response.headers.entries()) {
  const lowerKey = key.toLowerCase();
  if (lowerKey !== 'set-cookie' && lowerKey !== 'content-length') {
    void reply.header(key, value);
  }
}
```

Dessa forma, o Fastify recalcula deterministicamente o `content-length` exato com base no payload final transformado.

## 4. Medição de Consultas e Caching de Sessão (T24 e T27)

### Curto-circuito do Hook (`shouldResolveSession`) (GAP-13)

Endpoints que não exigem resolução de sessão não acionam o Better Auth:

- `/health` e `/health/ready` (evita amplificação de consultas sob DDoS ou probes).
- `/api/auth/*` (a rota coringa do Better Auth já resolve a sessão internamente se necessário).

### Cache de Cookie (`session.cookieCache`)

Habilitado em `auth.config.ts`:

```ts
session: {
  expiresIn: 60 * 60 * 24 * 7,
  updateAge: 60 * 60 * 24,
  cookieCache: { enabled: true, maxAge: 5 * 60 },
}
```

### Metodologia de Medição em T24 e T27

Nos testes de integração (`tests/integration/auth-error-envelope.test.ts`), espionamos o método `pool.query` do `pg.Pool` da aplicação:

```ts
const querySpy = vi.spyOn(pool, 'query');
```

- **T24 (`GET /health` com header `Authorization` forjado):** Provou 0 consultas SQL contendo `session`. O curto-circuito previne totalmente a amplificação no banco de dados.
- **T27 (Duas requisições sucessivas a `/api/v1/me` com cookie válido dentro de 5 min):** A 1ª requisição consulta o banco para carregar a sessão; a 2ª requisição reutiliza o `better-auth.session_data` (cache assinado), gerando exatamente 0 consultas na tabela `session`.

## 5. Achado R-01: Injeção de `request.ip` Validado e Verificação Manual em Socket Real

### Causa Raiz de R-01

A ponte Fastify/Fetch montava o `Request` apenas com headers, sem repassar o IP do socket. O Better Auth lia o header cru `x-forwarded-for` do cliente. Um cliente fora da borda podia forjar `x-forwarded-for: 6.6.6.6` e burlar os buckets de rate limit ou gravar IPs falsos em `session.ip_address`.

### Correção

1. `toFetchHeaders(incoming, clientIp)` agora sobrescreve `x-forwarded-for` com `set()` (nunca `append`) quando `clientIp` é fornecido.
2. Ambos os call sites de `auth.plugin.ts` (a rota coringa e o hook `onRequest`) passam `request.ip` validado pelo Fastify via D-60.

### Por que `advanced.ipAddress.trustedProxies` foi mantido em `auth.config.ts` (Armadilha 14)

Embora o IP repassado já seja validado pelo predicado do Fastify, manter `advanced.ipAddress` no Better Auth fornece **defesa em profundidade**: caso uma alteração futura acidentalmente remova o parâmetro `request.ip` de algum call site, a validação de CIDR no Better Auth impede que valores arbitrários sejam aceitos. **Não deve ser removido por falsa impressão de redundância.**

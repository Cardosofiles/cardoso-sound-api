## 1. O que foi entregue

Este sprint fechou 7 GAPs de segurança auditados em `docs/issue/AUTHENTICATION.md`:

1. **GAP-08 (Anti-enumeração de e-mail no sign-up):** `POST /api/auth/sign-up/email` retorna status 200 idêntico e corpo sintético indiferenciável quando o e-mail já existe na base.
2. **GAP-14 / D-51 (Revoga D-46 a):** `POST /api/auth/sign-in/email` retorna **403 Forbidden** enquanto `emailVerified === false`.
3. **GAP-07 / D-52 (Revoga D-46 e):** `POST /api/auth/reset-password` revoga todas as sessões anteriores ativas no banco de dados (`revokeSessionsOnPasswordReset: true`).
4. **GAP-15 (Política de senhas fracas e limitação de tamanho):** Bloqueio offline de senhas comuns (`isWeakPassword`) com HTTP 400 em `/sign-up/email`, `/reset-password` e `/change-password`, além de teto de 128 caracteres contra DoS.
5. **GAP-22 (Defesa em profundidade nos templates de e-mail):** Escape real de caracteres sensíveis (`&`, `"`, `'`, `<`, `>`) no atributo `href` via `escapeHtmlAttribute`.
6. **GAP-24 (Cobertura de troca de senha autenticada):** Suíte dedicada `tests/integration/auth-change-password.test.ts` cobrindo `POST /api/auth/change-password` (T14–T19).
7. **GAP-25 / D-57 (Logger sanitizado no Mailer sem instância local de Pino):** Remoção de `pino()` isolado em `src/shared/email/mailer.ts`, com injeção tipada de `MailerLogger` e garantia estrita de zero vazamento de URLs ou destinatários em logs.

## 2. Mudanças de Contrato HTTP e Impacto para Clientes (Flutter / Web)

### 2.1 `POST /api/auth/sign-up/email`

- **Antes (F3):** Retornava 200 com `token` preenchido e sessão iniciada para e-mail novo; retornava 4xx para e-mail já existente.
- **Agora (F5-S03 — GAP-08 e GAP-14):**
  - Para e-mail novo: retorna **200 OK** com `{ user: { ... }, token: null }` e **nenhum cookie de sessão**.
  - Para e-mail já existente: retorna **200 OK** idêntico com dados sintéticos mascarados e `token: null`.
  - **Ação requerida pelo cliente Flutter:** Não assumir sessão logada após o sign-up. A interface deve exibir mensagem informativa solicitando que o usuário acesse sua caixa de entrada e clique no link de confirmação antes de realizar login.

### 2.2 `POST /api/auth/sign-in/email`

- **Antes (F3):** Aceitava login imediatamente sem exigir confirmação de e-mail.
- **Agora (F5-S03 — GAP-14):**
  - Retorna **403 Forbidden** (`{ "message": "Email not verified", "code": "EMAIL_NOT_VERIFIED" }`) se o usuário tentar autenticar antes de verificar o e-mail via token/link.
  - Retorna **200 OK** com `set-auth-token` e cookies de sessão após a verificação ser confirmada.

### 2.3 `POST /api/auth/reset-password`

- **Antes (F3):** Sessões ativas anteriores continuavam válidas na base após a redefinição de senha.
- **Agora (F5-S03 — GAP-07):**
  - Ao redefinir a senha, todas as sessões anteriores do usuário são sumariamente revogadas do PostgreSQL.
  - Qualquer token de portador (`Bearer`) ou cookie de sessão anterior passa a responder **401 Unauthorized**.

### 2.4 `POST /api/auth/change-password`

- **Contrato:**
  - Exige usuário autenticado via Bearer ou cookie (responde **401** sem credencial).
  - Requer `{ currentPassword, newPassword, revokeOtherSessions?: boolean }`.
  - Rejeita senha atual incorreta com **400 Bad Request**.
  - Rejeita nova senha fraca ou menor que 8 caracteres com **400 Bad Request**.
  - Quando `revokeOtherSessions: true`, revoga as demais sessões ativas do usuário.

## 3. Comportamento de Runtime do Better Auth e Helper E2E

### 3.1 Token `null` no Sign-up

No Better Auth v1.7.2, ao configurar `requireEmailVerification: true`, a lib executa internamente (`sign-up.mjs:164`):

```javascript
shouldSkipAutoSignIn = true;
```

Portanto, a resposta de cadastro **nunca** emite token de sessão.

### 3.2 Novo Helper E2E em 4 Passos

Para garantir que testes E2E e de integração autentiquem deterministicamente sem dependências externas, o helper `signUpAndGetToken(app, email)` em `tests/e2e/helpers/auth.ts` foi refatorado para executar o fluxo real em 4 passos offline:

1. `POST /api/auth/sign-up/email`: registra o usuário e dispara o e-mail no `outbox` em memória.
2. Leitura do `outbox`: extrai a URL e o token descartável do atributo `href` do e-mail.
3. `GET /api/auth/verify-email?token=...`: confirma a titularidade da conta.
4. `POST /api/auth/sign-in/email`: autentica com senha forte (`StrongP@ssw0rd!2026#F5S03`) e extrai o Bearer token e cookies de sessão.

## 4. Racional da Política de Senhas Fracas Offline (GAP-15)

1. **Inviabilidade do plugin `haveIBeenPwned` em testes e resiliência:**
   - O plugin nativo do Better Auth consulta a API pública Pwned Passwords via HTTP síncrono.
   - Em caso de falha de conectividade ou indisponibilidade da API externa, o plugin lança exceção com HTTP 500 (_fail-closed_ não tolerante a falhas), inviabilizando suítes de teste desconectadas do CI e tornando o sign-up refém de terceiros.
2. **Solução implementada:**
   - Conjunto canônico offline em `src/shared/security/weak-passwords.ts` contendo as senhas mais exploradas em vazamentos globais.
   - Checagem em tempo constante $O(1)$ através de `Set.has(password.toLowerCase())`.
   - Interceptação elegante via middleware de autenticação (`weakPasswordPlugin`) registrado em `auth.config.ts` cobrindo `/sign-up/email`, `/reset-password` e `/change-password`.
   - Em conformidade com o NIST SP 800-63B, não foram adicionadas restrições artificiais de composição (números, maiúsculas, símbolos).

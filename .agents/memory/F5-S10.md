## 3. Metodologia de Medição dos Casos Críticos (T11 e T14) — Para o Time Flutter

Esta seção documenta com precisão técnica a forma como os comportamentos de segurança foram medidos nas suítes automatizadas, servindo de guia para o desenvolvimento do app móvel.

### Como T11 (`allowDifferentEmails: true`) foi medido

1. O objetivo do teste de integração foi garantir que identidades providas por provedores distintos com e-mails diferentes coexistam harmoniosamente na conta do usuário, sem gerar rejeição de integridade ou bloqueio de listagem.
2. Criou-se um usuário primário com `cadastrado@exemplo.com`.
3. Inseriu-se diretamente no banco (tabela `account`) uma credencial com `providerId: 'github'`, simulando o estado final pós-autenticação OAuth com e-mail secundário.
4. Ao consultar `GET /api/auth/list-accounts` (R46), o endpoint devolveu status 200 com array contendo ambas as credenciais (`credential` e `github`), provando que a convivência de e-mails múltiplos é válida e exposta de forma isolada.
5. Ao acionar `POST /api/auth/link-social` com provedor Google, o erro retornado pela API **não** foi `LINKING_DIFFERENT_EMAILS_NOT_ALLOWED` (que ocorreria se `allowDifferentEmails` estivesse desligado), e o teste unitário T2 atesta de forma canônica que `options.account.accountLinking.allowDifferentEmails === true`.

### Como T14 (Sessão Antiga e Step-up) foi medido

1. O Better Auth assina o token retornado ao cliente no header `set-auth-token` usando uma assinatura HMAC (`<token_hash>.<assinatura>`).
2. Para envelhecer a sessão com determinismo no PostgreSQL, o teste executou:
   ```sql
   UPDATE session SET created_at = now() - interval '25 hours' WHERE user_id = $1;
   ```
3. A chamada a `POST /api/auth/unlink-account` foi enviada obrigatoriamente com o cabeçalho `Authorization: Bearer <token>`. Isso garante que a resolução da sessão ignore o cache de cookies em memória (`cookieCache` de 5 min) e consulte o registro real no PostgreSQL, onde `created_at` tem mais de 24 horas.
4. O middleware `freshSessionMiddleware` identificou que o carimbo de data/hora ultrapassou `freshAge: 86400` e rejeitou a requisição com HTTP `403 Forbidden` (`code: "SESSION_NOT_FRESH"`).
5. Em seguida (T15), o teste realizou novo sign-in por e-mail com senha (`StrongP@ssw0rd!2026#F5S03`), obtendo um token novo cuja sessão é recente (`created_at` atual). A repetição do `unlink` com este token resultou em `200 OK` (`{ "status": true }`), comprovando o fluxo de step-up authentication.

## 4. Catálogo de Respostas e Erros da API (T13, T14, T16, T18)

Todas as respostas abaixo foram capturadas diretamente das execuções reais de teste e do middleware `toRfc7807` de `src/modules/auth/auth.plugin.ts`:

### T13: Rejeição de Vínculo com Facebook (D-58 b)

- **Requisição:** `POST /api/auth/link-social` com `{ "provider": "facebook", "idToken": { ... } }`
- **Status HTTP:** `401 Unauthorized`
- **Payload retornado:**
  ```json
  {
    "message": "Account not linked - linking not allowed",
    "code": "LINKING_NOT_ALLOWED",
    "statusCode": 401,
    "error": "Unauthorized",
    "details": null
  }
  ```
- **Nota técnica:** O Facebook não está incluído em `trustedProviders` e não fornece garantia confiável de `emailVerified: true`.

### T14: Sessão Não Fresca (Exigência de Step-Up)

- **Requisição:** `POST /api/auth/unlink-account` com sessão emitida há mais de 24 horas
- **Status HTTP:** `403 Forbidden`
- **Payload retornado:**
  ```json
  {
    "message": "Session is not fresh",
    "code": "SESSION_NOT_FRESH",
    "statusCode": 403,
    "error": "Forbidden",
    "details": null
  }
  ```
- **Ação esperada do Flutter:** Exibir prompt solicitando a senha da conta ou reautenticação biométrica e repetir a operação após novo sign-in.

### T16: Tentativa de Vincular Provedor Sem Suporte a `idToken` (GitHub)

- **Requisição:** `POST /api/auth/link-social` com `{ "provider": "github", "idToken": { ... } }`
- **Status HTTP:** `404 Not Found`
- **Payload retornado:**
  ```json
  {
    "message": "id_token not supported",
    "code": "ID_TOKEN_NOT_SUPPORTED",
    "statusCode": 404,
    "error": "Not Found",
    "details": null
  }
  ```
- **Nota técnica:** O fluxo de vinculação do GitHub deve utilizar redirecionamento OAuth (`callbackURL`), nunca `idToken`.

### T18: Provedor Não Configurado (Exemplo: Twitter)

- **Requisição:** `POST /api/auth/link-social` com `{ "provider": "twitter", "callbackURL": "..." }`
- **Status HTTP:** `404 Not Found`
- **Payload retornado:**
  ```json
  {
    "message": "Provider not found",
    "code": "PROVIDER_NOT_FOUND",
    "statusCode": 404,
    "error": "Not Found",
    "details": null
  }
  ```

### T12: Proteção IDOR em Desvínculo de Contas

- **Requisição:** `POST /api/auth/unlink-account` com `accountId` de outro usuário ou UUID aleatório
- **Status HTTP:** `400 Bad Request`
- **Payload retornado:**
  ```json
  {
    "message": "Account not found",
    "code": "ACCOUNT_NOT_FOUND",
    "statusCode": 400,
    "error": "Bad Request",
    "details": null
  }
  ```
- **Nota de conformidade:** Identificador alheio e inexistente respondem de forma idêntica (`ACCOUNT_NOT_FOUND`), impedindo vazamento de existência ou enumeração de contas por terceiros (D-31).
